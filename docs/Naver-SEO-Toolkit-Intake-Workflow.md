# Naver SEO Toolkit — 의뢰서 기반 표준 작업 흐름 v1

## 목적
이 문서는 고객 문의를 공통 데이터로 정리하고, 사이트 환경과 관계없이 같은 수주·작업·납품 절차를 실행하기 위한 최소 운영 기준이다.

**핵심 원칙:** 의뢰서가 업무의 시작점이다. 환경 탐지기는 의뢰서에 기재된 URL을 분석하며, 실제 적용 방식은 탐지 결과와 고객의 접근 권한을 확인한 후 선택한다.

## 입력 문서
- `templates/01_customer_inquiry_quote.md` — 최초 문의·견적용. 기술 지식이 없는 고객도 작성 가능하다.
- `templates/02_customer_technical_handoff.md` — 견적 수락·계약 후 권한과 배포 환경 확인용.
- `templates/03_internal_intake_review.md` — 내부 적합성 판단용.

## 단계별 처리
| 단계 | 입력 | 실행 | 결과 | 다음 단계 조건 |
|---|---|---|---|---|
| 1. 의뢰 접수 | 고객 의뢰서 | 필수 항목 확인, 고객 기대 결과 식별 | 표준 의뢰 정보 | URL·요구 작업·검색 화면/검색어 확인 또는 부족 항목 요청 |
| 2. 사전 분석 | URL, 승인된 공개 분석 범위 | CMS/프레임워크 탐지, 공개 SEO·콘텐츠 상태 확인 | 환경 분석·기술 진단 | 분석 결과 또는 분석 불가 사유 확보 |
| 3. 수주 판정 | 의뢰 정보 + 분석 결과 | 가능한 납품 범위, 예상 난이도·제약·자료 누락 분류 | READY / NEED_INFO / CUSTOM_QUOTE / OUT_OF_SCOPE | 작업 범위와 제외 사항 명확화 |
| 4. 견적 확정 | 작업 범위 | 작업 항목·산출물·일정·비용·검수 기준 협의 | 합의된 견적·작업 명세 | 고객 승인 |
| 5. 기술 인계 | 기술정보 확인서 | 권한·백업·배포 경로·콘텐츠 사용 승인 확인 | 승인된 실행 계획 | 수정 권한·백업·롤백 확보 |
| 6. 구현 | 실행 계획 + 실제 콘텐츠 | 공통 최적화 산출물 생성, 환경별 어댑터로 적용 | 코드/메타데이터/이미지·변경 내역 | 기술 검증 통과 |
| 7. 검증·납품 | 변경 전후 자료 | SEO·JSON-LD·이미지·링크·회귀 검증, 고객 확인 | 검수 결과와 보고서 | 합의된 납품 기준 충족 |

## 의뢰서의 필드가 개발 행동으로 연결되는 방식
| 의뢰 항목 | 프로그램 동작 |
|---|---|
| 홈페이지 URL | Environment Detector 입력 및 분석 범위 설정 |
| 원하는 검색 화면의 캡처, 검색어, PC/모바일 | 캐러셀 가능 여부·검색 결과 유형 구별; 약속 가능한 결과와 구별 |
| 작업 종류: 캐러셀·SEO·이미지 | 필요한 모듈만 실행, 불필요한 작업 생략 |
| 캐러셀 표시 대상·목록/상세 페이지 | 실제 콘텐츠·URL·이미지 연결 가능성 검사 |
| 이미지 준비 여부·게시 권리 | 최적화·신규 제작 필요성·승인 요청 판단 |
| 수정 담당자·CMS 정보(선택) | 자동 탐지 결과와 대조, 접근 경로 확인 |
| 일정·예산 | 범위 및 견적 협의 시 사용; 자동 확정 금지 |

## 최소 표준 작업 데이터 (예시, 실제 고객 정보 아님)
```json
{
  "job_id": "JOB-EXAMPLE-001",
  "status": "INTAKE_RECEIVED",
  "request": {
    "site_url": "https://example-hospital.co.kr",
    "industry": "hospital",
    "requested_services": ["carousel", "seo", "images"],
    "target_queries": ["XX병원"],
    "reference_result": {"screenshot_received": true, "device": "mobile"},
    "content_type": "medical_staff",
    "candidate_page_urls": [],
    "images_available": "unknown"
  },
  "assessment": {
    "platform": "UNKNOWN",
    "confidence": "UNKNOWN",
    "evidence": [],
    "deployment_access": "NOT_VERIFIED",
    "decision": "PENDING"
  },
  "next_actions": ["Run read-only environment detection", "Identify missing information"]
}
```

## 모듈 연결 규칙
1. **Intake → Detector:** `request.site_url`이 기술 탐지의 기본 입력이다. 고객이 기재한 CMS는 참고 정보이고 탐지 사실과 구분한다.
2. **Detector → Assessor:** 감지한 환경의 증거·불확실성과 SEO 진단을 합쳐 작업 가능성을 판정한다.
3. **Assessor → Quote:** 지원되는 작업, 필요 자료, 제외 사항 및 수동 작업량을 확정한 후 견적을 작성한다.
4. **Approved Scope → Builder/Adapter:** 고객이 승인한 작업만 생성·적용한다. 승인 전까지 읽기 전용으로 유지한다.
5. **Verifier → Delivery:** 적용 결과와 고객이 기대한 검색 화면을 구분해 보고한다.

## 중요한 제약
- 검색 결과의 실제 캐러셀 표시, 순위, 노출 시점은 보장하지 않는다.
- 고객이 희망하는 카드형 검색 UI가 반드시 같은 구조화 데이터 유형인 것은 아니다. 참고 스크린샷을 분류해야 한다.
- 의료·법률 등 규제 업종의 콘텐츠는 고객의 사실관계·광고 심의를 거친다.
- 최초 의뢰 단계에서 관리자 암호, API 토큰, 환자 정보 등 민감 정보를 받지 않는다.
- 실제 작업 데이터와 고객 연락처, 권한 정보는 Git에 커밋하지 않는다. 저장 시 접근 제어와 보존·파기 기준을 적용한다.
- 고객 URL의 공개 영역에 대한 비침투적 분석부터 시작한다. 자동 수정은 명시적 승인 후 진행한다.

## 이번 구현에서 할 일 / 하지 않을 일
**할 일:** 기존 3개 양식을 유지하며, 최초 의뢰 내용을 구조화된 작업 정보로 변환할 수 있도록 필드 명세를 확정한다. Environment Detector가 URL을 받는 기존 CLI 기능은 그대로 유지하되 이후 작업 정보 연동 경로를 마련한다.

**하지 않을 일:** 새 대시보드, 고객 회원가입, 결제, CRM, 견적 가격 자동 확정, 무조건적인 CMS 자동 배포, 3인 에이전트 체제.

## 검증 기준
- 서로 다른 업종·CMS의 가상 의뢰 2~3건을 같은 형태로 표현할 수 있다.
- 고객이 CMS를 몰라도 접수하고 분석할 수 있다.
- 부족한 자료가 무엇인지 구체적으로 도출할 수 있다.
- 아직 계약되지 않은 건은 외부 사이트에 어떠한 수정도 수행하지 않는다.
- 후속 구현·납품 항목이 실제 의뢰 범위와 연결된다.
